# Clinical Data Intelligence Platform

> 🏆 **3rd Place · Secure AI Hackathon 2026** (Seattle Data AI & Security · Track 3 — Human-in-the-Loop AI)

AI-powered pipeline that ingests raw EHR data, normalizes it to HL7 FHIR R4, generates clinical summaries via Claude API, and surfaces a semantic search interface for clinicians — with a **human-in-the-loop review layer** so no AI-generated summary reaches a clinician's decision without explicit approval and full audit trail.

## Hackathon Disclosure (Secure AI Hackathon, 2026-07-30 → 2026-08-01)

**Track:** Track 3 — Human-in-the-Loop AI Assistant

**Pre-existing work (before hackathon kickoff at 2026-07-30 10:00 AM):**
- EHR data ingestion, cleaning, Pydantic validation
- FHIR R4 normalization (Patient, Encounter, DiagnosticReport, DocumentReference)
- Claude API summarization with SQLite/JSON cache
- Sentence-transformer embeddings + ChromaDB semantic search
- FastAPI backend, Vanilla JS + Tailwind frontend
- 75 unit + integration tests

**Built during the 48-hour hackathon:**
- Review queue: every AI summary starts as "pending"; reviewers explicitly approve / edit / reject before it is trusted
- Audit log: every view, approval, edit, and rejection is persisted with actor, timestamp, and content hash
- Fact grounding: each summary claim is matched against source FHIR resources; ungrounded claims are flagged as potential hallucinations with clickable evidence trail
- Cross-vendor verification (v2, full source): all 33 Claude-generated summaries were independently reviewed by OpenAI GPT-5.6-terra against the complete source FHIR bundle. Result: 4 approve, 28 edit, 1 reject; 104 hallucinated claims found — dominated by fabricated BMI numeric values and blood-pressure readings that don't exist in the source data. Full data in `data/verifications.json`.
- PII masking layer with toggle (names, MRNs, DOBs masked by default)
- Safe refusal when source data is insufficient
- Role-based review controls (clinician vs reviewer)
- HIPAA-aligned session management: server-issued session tokens, 15-minute idle timeout with client-side countdown, automatic logout on expiry, `X-Session-Token` header enforced on every PHI-touching endpoint (401 without valid token). Login and logout events written to the audit log.

                 │  Session (login · PBKDF2 · 15-min idle timer)  │
                 │  Role-gated (clinician vs reviewer)            │
                 └────────────────────────────────────────────────┘
                                       │
Synthea EHR data → Ingestion → FHIR R4 → Claude Opus summarize
                                              │
                                  ┌───────────┴───────────┐
                                  ↓                       ↓
                        Fact grounding             Cross-vendor verify
                        (source ↔ claim)           (OpenAI GPT-5.6-terra)
                                  └───────────┬───────────┘
                                              ↓
                                   Human review queue
                                 (approve · edit · reject)
                                              ↓
                                       Audit log
                          (login · view · toggle · decision · content hash)
```

**48-hour build**: everything from the session box down through audit log (grounding, cross-vendor verify, review queue, PII masking, role gating, auth, audit).
**Pre-existing** (disclosed above): the FHIR ingestion pipeline, Claude summarizer, and ChromaDB search that the trust stack sits on top of.

# Open http://localhost:8000
```

## Design Decisions

### Data Generation
Used Synthea to generate realistic synthetic patient records with varied clinical scenarios. Records are exported as FHIR JSON, then deliberately "dirtied" into JSON + CSV formats with inconsistent dates, mixed gender codes, and duplicate entries to exercise the cleaning pipeline.

### FHIR R4 with fhir.resources v8
Chose `fhir.resources` v8 (FHIR R5-compatible) over `fhirclient` for its Pydantic v2 integration and strict schema validation. All resources are validated via `model_validate()` round-trip. Four resource types are mapped: Patient, Encounter, DiagnosticReport, and DocumentReference.

### Dual Summary Pipeline
Summaries are generated by calling the Claude API (`claude-opus-4-6`) with a structured JSON prompt that enforces field requirements and a 200-word limit. Generated results are cached in `data/summaries.json` for the demo. The summarizer pipeline (`app/summarizer/pipeline.py`) can regenerate summaries with any Anthropic API key.

### Embedding & Search
Used `all-MiniLM-L6-v2` for its balance of speed and quality on clinical text. ChromaDB was chosen over FAISS for its persistent storage and metadata filtering. Both FHIR document text and AI summaries are embedded, so semantic search covers the full patient record. Per-patient deduplication ensures search results show one card per patient with the most recent matching record.

### Frontend
Single HTML file with Tailwind CSS CDN and Vanilla JS, no build step required. Real-time debounced search (400ms), slide-out patient detail panel with AI summary + FHIR resource browser + matching record history. ARIA labels, keyboard navigation, and responsive layout for accessibility.
